# product-pulse disabled in aeon.yml — no fresh product state for 15 days

## Symptom

`memory/topics/product-pulse-state.json` `last_run` frozen at **2026-06-25T07:15:00Z**.
No `articles/product-pulse-YYYY-MM-DD.md` written since 2026-06-25.
war-room has flagged "product-pulse dark" on 3+ consecutive mornings (07-07 → 07-09),
escalating from note → issue per the 07-09 log ("if it doesn't run tomorrow, file an issue").

Effect on the brief: STATE has no current X-follower deltas and no live verification of
the `aeon-wc` private-core stall (last-known 2026-06-08, now 32d). Star counts survive
only because `mention-radar` (07-08) and `shiplog` (07-09) independently pull them.

## Root cause

`aeon.yml`:

```yaml
product-pulse: { enabled: false, schedule: "15 7 * * *", var: "" } # 07:15 UTC — ...
```

`enabled: false` → the daily 07:15 cron never dispatches. This is a config flip, not a
transient runner/API failure (bd-radar, on the adjacent 07:20 cron, runs clean daily).
The surrounding comment block (lines 424–425, 480–484) still describes product-pulse as
the active 07:15 leg of the staggered war-room trio, so the disable reads as accidental —
likely collateral from the 2026-06-29 catalog-parity sync that set a batch of skills
`enabled: false`.

## Fix

One-line flip in `aeon.yml`:

```yaml
product-pulse: { enabled: true, schedule: "15 7 * * *", var: "" }
```

Operator decision (it's their workflow-enable config) — war-room files, does not flip.
After re-enable, confirm the next 07:15 run writes `product-pulse-<date>.md` and advances
`product-pulse-state.json` `last_run`, then resolve.

## Verification

- [ ] Set `product-pulse.enabled: true` in aeon.yml (PR).
- [ ] Next 07:15 UTC run produces a fresh digest + advances state `last_run`.
- [ ] war-room STATE pulls live follower deltas + aeon-wc age from the fresh pulse.
